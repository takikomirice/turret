> この文書は学校のPCで実装するための引き継ぎ資料。作成時点では計画のみで、統合実装・GAS反映は行っていない。実装方法は学校側の環境に合わせる。

**Goal:** turret に既存の採点用「型枠」を組み込み、フォーム作成・配付から採点・日次返却までを一つのGASで運用する。追加要件として、フォーム配付用のClassroom「資料」の予約投稿を実装する。

**Architecture:** 管理画面と採点画面を別々のHTMLとして同じWebアプリから提供する。scoring_tool の操作感と講評生成を活かし、対象回答シート・設定・サーバー処理を turret と接続する。採点済み判定と日次返却の取り決めは維持する。

**Tech Stack:** Google Apps Script（V8）、HTML/CSS/JavaScript、Google Sheets / Forms / Classroom、既存のNode.jsテスト。

**Spec:** 本書「1. 合意した要件」が今回の会話で確定した仕様。実装上の構成・関数名は「3」以降の提案であり、合意済み要件と区別する。追加の資料予約投稿は「10」に設計案を記載する。

## 1. 合意した要件

### 目的と日常の操作

- turret はフォーム作成・配付と、生徒ごとの限定お知らせによる評価返却を担当している。
- scoring_tool は、生徒の回答行から採点に必要な部分だけを表示し、指定した入力枠で評価と講評を記入する「採点の型枠」である。
- 毎日の操作は、設定済みの採点画面をブックマークから直接開き、採点して保存する。毎回管理画面を経由させない。
- 設定・管理画面と採点画面は分けたまま、一つのGASプロジェクトに統合する。
- 既存の自動講評は型枠の中核として移植対象に含める。単なる点数入力画面への縮小や、全面的なUI作り直しはしない。

### 維持する採点・返却の取り決め

- turret は、指定した採点済み判定セルに値がある回答を、未処理などの既存条件と合わせて取り込む。空なら取り込まない。
- 自動返却は一日一回、教員が採点していない時間帯に実行する。既存の取り込み・送信のスケジュール設定を維持する。
- 新たな「採点確定」ボタンや「未採点→採点中→確定」という必須ワークフローは導入しない。
- 保存しただけで即時返却する仕組みには変えない。
- 統合を理由に、取り込み済みデータ・生成済み本文・送信済み投稿を自動更新・自動再送しない。

### 採点画面のシート候補

- 切替候補には、採点対象となるフォーム回答シートだけを出す。
- クラス一覧、生徒一覧、対応表、評価データ、送信シート、エラーログ、フォーム管理、設定用シート、`_templates`、`_rules` などのシステム用シートは出さない。
- スプレッドシート上でシート自体を非表示にする必要はない。採点画面の候補だけを絞る。
- 古い選択情報などで対象外シートを指定しても、採点データとして読み込んだり、点数・講評を書き込んだりしない。
- 対象がない場合は「対象の回答シートがありません」と表示する。先頭の任意シートへフォールバックしない。

### 追加要件：フォーム配付用の資料予約投稿

- 対象はClassroomの「授業」に投稿する、フォーム配付用の「資料」。ユーザー確認済み。
- 配付日時を指定して予約投稿できるようにする。既存の即時投稿も維持する。
- 採点結果の「限定お知らせ」の予約機能追加は対象外。既存の日次返却を維持する。
- 予約機能も同じGAS・既存の管理画面へ組み込み、配置ファイルを増やさない。

### Global Constraints

- 学校の環境では clasp を利用できない。Apps Scriptエディタへの手動コピペで導入・更新できること。
- 配置対象は `appsscript.json` を含めて原則5ファイル以内。ビルドやclaspを必須にしない。
- 5ファイルを超える必要が生じたら、実装で増やす前に理由・ファイル数・構成案をユーザーへ説明して相談する。
- ローカルのテスト・ドキュメント・設定サンプルは配置ファイル数に含めない。
- 既存の本人限定Web管理画面の認証・実行者条件を採点画面でも維持する。
- 今回はリポジトリ削除、scoring_tool 単独版の廃止、複数教員の共同採点、返却後の訂正機能の新設は行わない。

## 4. 画面の入口と設定の扱い

### Web入口

`doGet(e)` を一つだけ置き、明示的な分岐でHTMLを返す。

| URL末尾 | 動作 |
| --- | --- |
| `/exec` | 既存互換として管理画面を開く |
| `/exec?page=settings` | 管理画面を開く |
| `/exec?page=scoring` | 採点画面を直接開く。日常用のブックマーク先 |

不明な `page` は管理画面に戻す。パラメータをそのままHTMLファイル名として使用しない。既存のWeb画面用コンテキスト設定とURL記録を維持する。統合版への移行時には採点用ブックマークを一度差し替える。

### 設定

- 回答先・クラス対応・返却項目・採点済み判定は turret 側を正とする。採点画面に別の自由な接続先設定を重複して持たせない。
- 表示列、採点枠、項目ラベル、講評出力先、選択テンプレートなどの「型枠」の設定は維持する。返却項目と採点枠は役割が違うため、全項目を一対一に自動変換しない。
- 採点固有設定は `TURRET_SCORING_CONFIG` など専用の保存キーに分け、既存 `APP_CONFIG` を上書きしない。これは保存形式の提案であり、既存JSON互換を守れる同等案も可。
- 既存の採点設定JSONとテンプレパックを移行できるようにする。別GASのScriptPropertiesを自動で読める前提にしない。
- `_templates` / `_rules` は turret の運用スプレッドシートに置く。初期化・インポートの既存データ保護を維持する。
- 枠の最大数（得点5、講評等3）、列重複の拒否、講評の手修正、キー操作、未送信データの保持は既存仕様を基準に移植する。
- 採点の列設定変更だけで、turret の採点済み判定列や返却本文を勝手に変更しない。

## 5. 回答シートの選定とAPI境界

統合用の対象一覧をサーバーで作り、一覧・読み込み・保存で同じ判定を使う。

推奨するインターフェース：

- `getScoringTargets_()` → `Array<{spreadsheetId, sheetId, sheetName, spreadsheetName}>`
- `resolveScoringTarget_(target)` → 対象内であることを検証したSheet。対象外・削除済み・アクセス不能ならエラー。
- `scoringGetTargets()` → 画面用の対象一覧。
- `scoringGetInitData({target, ...})` → 既存の初期表示データ。
- `scoringSaveRows({target, rows})` → 既存同様の行別保存結果。`target` は `{spreadsheetId, sheetId}`。

選定の方針：

1. turret が作成したフォームは、管理記録の回答先スプレッドシートと `responseSheetId` から実在する回答シートを特定する。
2. 既存フォームは、登録済み回答先・接頭辞を使う既存選定処理を活かす。
3. システム用シートを除外する。既存の除外に `_templates` / `_rules` を含め、外部の回答先にそれらがある場合も候補に出さない。
4. スプレッドシートID＋シートIDで重複を除く。同名タブが複数スプレッドシートにあっても取り違えないよう、画面には必要に応じてスプシ名を併記する。
5. 保存対象をクライアントのシート名だけで信用せず、読み込み・保存の都度、現在の対象一覧と照合する。

管理記録のIDで採点画面を開けても、手動改名により既存の返却対象の接頭辞から外れる場合がある。この場合は設定不一致を案内し、返却まで対象になっているように見せない。統合を理由に既存の返却対象範囲を黙って広げない。

localStorageの保存キーにも対象のスプレッドシートID＋シートIDを含め、別シートの下書きを混ぜない。保存中の対象切替でも、送信開始時の対象を固定する。旧単独版のブラウザ下書きは自動移行を前提とせず、旧版でシートへの保存を完了してから切り替える。

なお、現在の回答行識別は行番号に依存している。物理的な行並べ替えを安全にするための恒久的な回答ID導入は今回の範囲に含めず、採点画面に元シートの物理ソートを追加しない。

## 10. 追加設計案：Classroom資料の予約投稿

採点統合とは独立して確認できる追加機能として実装する。対象は `CourseWorkMaterials` であり、成績返却の `Announcements` には予約処理を追加しない。

### 予約の基本方式

- Google公式の `CourseWorkMaterial.scheduledTime` を使用する方式を第一候補とする。GAS側で資料公開用の時刻トリガーを多数作る方式は初期案にしない。
- 予約作成は `DRAFT` と未来の `scheduledTime` を指定する案とし、学校のテストGASで実際の予約動作を確認して採用する。
- 画面では日本時間で年月日・時刻を入力し、API境界でRFC 3339へ変換する。過去日時・空欄・不正日時は予約実行前に拒否する。
- 複数クラスへの投稿では共通の予約日時を指定し、各クラスの成功・失敗・確認待ちを別々に記録する。クラス別の日時指定は初期実装の必須要件にしない。
- Classroomに予約を登録できた時点を「予約済み」、APIで公開を確認した状態を「投稿済み」とする。予定時刻を過ぎたという理由だけで投稿済みに書き換えない。
- 日時変更には `scheduledTime` の更新を使う。取消は予約解除して下書きを保持する案を優先し、APIで解除可能か実機確認する。対応できない場合の削除方式は、実装前に利用者へ動作を説明する。
- 投稿ID・予定日時・最終確認状態を管理記録に保持する。作成結果が不明なら確認待ちにし、同じ資料を自動で作り直さない。既存の照合は `PUBLISHED` 前提なので、予約中の `DRAFT` と予定日時も照合できるようにする。

`scheduledTime` は公式の資料リソースに定義され、`patch` の更新対象にも含まれている。ただし、予約・変更・解除と実際の公開結果は学校側で実機確認する。[資料リソース](https://developers.google.com/workspace/classroom/reference/rest/v1/courses.courseWorkMaterials)、[資料の更新](https://developers.google.com/workspace/classroom/reference/rest/v1/courses.courseWorkMaterials/patch)。

### フォーム公開・受付との関係：実装前に選ぶ事項

現在の即時投稿は、フォームの公開・受付開始と資料の公開を一続きで実行する。Classroomの資料予約は、Googleフォーム自体の公開・受付開始を予約する機能ではない。

推奨する初期案は、予約登録時にフォームを公開・受付可能にしてリンク先を準備し、資料の配付だけをClassroomで予約する方式。この案では、予約前でもフォームURLを知っている許可済みユーザーは回答できるため、「フォームは受付中／資料は○月○日○時に公開」と画面に明記する。**この受付時刻はまだユーザー合意事項ではない。実装前に確認する。**

予約時刻までフォームへの直接回答も禁止する必要があれば、フォーム受付開始の別処理を設計する。その場合は資料公開との時刻差・受付開始失敗・予約変更／取消時の連動も検証し、同時刻に必ず完了すると保証しない。

どちらの方式でも、資料予約の取消だけで既存回答を消さない。フォーム受付を自動停止するかどうかも、選んだ方式に合わせて明示する。
