# High-priority reliability implementation plan

**Goal:** 調査で優先度「高」とした6件を修正し、既存のメニュー、画面、シート列、通常の操作順を維持する。

**Architecture:** `Code.gs`内の既存処理を修正する。設定入力と旧設定の移行を区別し、更新処理を共通ロックで保護する。取り込み・送信準備は既存の元SS_ID・元シート名・元行番号で重複を検出する。送信前に確認待ち状態を永続化し、結果不明な投稿は自動再送しない。

**Tech stack:** Google Apps Script V8 / Node.js test runner / clasp 3.3.0。

**Spec:** 2026-09-28の調査結果とユーザー依頼。対象は投稿成功後の記録失敗、取込・準備の重複、同時実行、空欄設定の復活、設定行のずれ、本文列名衝突。UI再設計と中優先度の独立した修正は対象外。

## Constraints and decisions

- 本番・生徒・メールへの試験送信はしない。既存の公開関数名とシート列を維持する。
- 明示的に空にした接頭辞は対象なしとして処理を止める。全シートへ対象を広げない。シート/キーがない旧環境は従来の保存値へフォールバックする。
- 結果不明な送信は`送信確認待ち`とし、Classroomの確認後に手動で状態を解決する。投稿拒否が明確なレート制限のみ従来どおり再送可能とする。
- 元回答の並べ替え・行削除に耐える新IDの導入、既存キュー削除後の履歴保持は別改修。今回の重複照合は既存行を保持している範囲。
- UI確認ダイアログを開いたままロックを保持しない。更新処理のみロックし、必ず解放する。

## Review focus

- 後方にある送信済み行より前に重複した未送信行がある場合も再投稿しない。
- 送信前状態記録・flushに失敗したら外部投稿しない。
- 投稿後の記録失敗や不明なAPI結果を通常の未送信へ戻さない。
- 重複除外で不正な元行番号を同じ回答と誤認しない。
- 全設定消去、空の追加行、設定KEYの交互配置で別設定やメモを壊さない。

## Review follow-up

- 読取入口でもキャッシュ移行が設定保存と競合するため、設定読込と候補取得も共通ロックの対象とした。
- 全空欄の中間行はスキップし、旧設定のみの環境で初期シートを作るときは保存済みの3キーを引き継ぐ。双方で修正前の失敗を確認し、回帰テストを追加した。
- API応答不明と明確な拒否を区別する。単なる数値の部分一致でレート制限と判断しない。
- [Google公式のLock仕様](https://developers.google.com/apps-script/reference/lock/lock)に従い、ロック解放前と外部投稿前にflushする。[Ui仕様](https://developers.google.com/apps-script/reference/base/ui)上、alertによる中断中はロックが維持されないため、確認と結果表示はロックの外で行う。
- [Classroomのエラー分類](https://developers.google.com/workspace/classroom/troubleshooting/common-errors)を参照し、明確なレート制限だけを自動再試行する。ClassroomとSheetsを跨ぐ原子的な保証は行わず、不明な結果は手動確認で解決する。
