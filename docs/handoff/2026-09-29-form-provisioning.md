## 3. 実装済みの機能・守るべき仕様

- 日常処理はトリガー自動実行が中心。ユーザーが重視するのは初期設定・管理。メニュー順は初期設定、管理、手動実行。
- 管理画面は6ステップ：シート準備 → クラスと生徒 → フォームと通知先 → 列と項目 → メッセージ → 自動実行。
- 生徒取得と任意の対応表はクラスの手順へ統合。バックエンドの進捗IDは互換性のため8種類のまま。
- 上部ナビ・セットアップガイド・保存状態を固定。短い入力欄と折り畳み説明を使い、余白・重複説明・スクロール負荷を抑える。
- 上部「設定を保存・出力」に一括保存とJSON入出力。`saveSetupSections`はsources/fields/templateを一括検証・保存し、時間帯は別途明示確定する。
- 項目別 `fields[].gradeScale` に対応。未指定なら共通 `config.gradeScale` を継承、明示的な `[]` は空のまま。既存取り込み済みの評価・生成済み本文は自動再変換しない。
- JSONはv3を書き出し、v1/v2/v3を読み込み。新規の運用固有の列・項目・本文・評価変換は空から開始。旧設定を維持する。
- 既存設定や送信データを設定保存のためにクリアしない。保存の競合検出、失敗時の復旧、共通ロックを維持する。
- 投稿前に「送信確認待ち」を記録する。投稿成功後のシート更新失敗と投稿失敗を分け、結果不明の投稿を自動再送しない。
- 時刻は日本時間 `Asia/Tokyo`。初期値は取り込み5時台、準備・送信8時台、リマインダー16時台。希望時刻はダイアログのみで設定してよい。
- 同期設定・認証情報・個人データ・クラウド退避物はGitに入れない。

## 4. ユーザーの実運用

1. Googleフォームで質問項目を設定したひな形を作る。
2. クラス数分コピーし、タイトル・共有設定を決める。学校アカウント以外から回答できないよう制限している。
3. 各フォームの回答先を、一つの回答用スプレッドシートにまとめる。教科などによって回答用ファイルが複数ある例も画像で示された。
4. 各クラスのClassroom「授業」に、フォームのリンクと説明文を**「資料」**として投稿する。課題・テスト付き課題ではない。
5. 回答用スプレッドシートをturretに登録し、採点結果を取り込んで生徒へ個別返却する。

この準備を学期中間・期末などで繰り返しており、ここを省力化したい。

### ファイル配置

期間ごとの親フォルダ（例：`04授業振り返り(2学期末)`）直下にクラス別フォームと回答用スプレッドシートを配置。親フォルダ内の`固定砲台`サブフォルダにturretを置く。視認性のための配置であり、フォルダ移動や既存ファイル統合を依頼されたわけではない。

### 回答・採点シート

- 回答タブを `フォーム回答 1-1` のように、共通部分＋クラス名で命名する。
- **回答行の順序は変えていない。** 名前順や点数順への物理的な並べ替えはしていない。
- 右側に名前、評価、コメント、送信状態の列を教員が追加する。
- 名前はメールアドレスをキーに、名簿データへXLOOKUPして表示する。
- 回答開始後に関数を入れる手間が現在の問題。名簿の参照元が独立したスプレッドシートでも構わないという意向。
- Classroomの表示名を正式氏名として採用してよいかは未確認。現在の名簿を勝手にClassroom名簿で置換しない。
- 評価は現在1〜5を使っている。別途、旧来の評価集計GASがあるが、コードは未提供で未調査。**集計は今回対象外。**
- 想定規模は授業6限・最大240名程度、数日分を含め500件ほど。無用な複雑化・処理の重さを避けたい。

## 5. 次の実装に向けた方針

### ユーザーが明示した内容

- turretのクラス一覧で「同期対象(1)」が `1` のクラスを対象にフォームを作る。
- ひな形から複製し、回答先をまとめ、各クラスへ資料投稿する作業をつなげる。
- 作成時に分かるフォーム・クラス・回答先の情報を使い、URL貼付や対応付けを省く。
- 学期管理は当面システム複製でよい。高度な期間切替は先行させない。
- 評価集計は後回し。
- 送信用スプシ（turret）へ回答タブも集約する構成を許容する。

### 会話で提案した設計（実装計画の推奨案）

- 新規作成は**現在のturretスプレッドシート自身を回答先**にする。新しい回答専用スプシを別途作る工程を省く。
- クラスごとの回答タブは維持し、採点用の追加列を回答開始前に準備する。
- 外部の回答スプレッドシートを登録する既存機能は維持する。既存本番データの移動はしない。
- 名前の自動補完は、回答先スプシのフォーム送信トリガー＋不足行のまとめ直しを候補とする。XLOOKUP自体が技術的に回答前に置けない、と断定したものではない。
- 作成・確認とClassroomへの投稿を分ける。作っただけで投稿・回答受付・返却の自動実行を開始しない。
- 作成・投稿のIDと進捗を記録し、部分失敗後に既存の成果を再利用する。外部操作の結果不明は確認待ちとし、自動で二重作成・投稿しない。
- 回答受付のオン／オフはフォーム一覧から操作できるようにする。受付停止と採点結果の返却停止は別操作。
- 管理画面からクラス別の回答・採点タブを開けるようにする。

### 行番号管理の判断

現状は `元SS_ID + 元シート名 + 元行番号` で回答を識別する。回答行を動かさず、取り込み開始後にタブ名を変更しない運用なら、今回は維持する。右側への採点列追加だけなら行番号は変わらない。

新しい「フォーム作成・資料配布」の記録は、フォームID・クラスID・投稿IDを使う。シートに1行ずつ記録しても、行番号を識別子にはしない。**この話と、既存回答を永続回答IDに移行する話を混同しない。**

## 6. 実装前に確認する情報

フォーム配布先の種類は「資料」で確定しているため再質問しない。次は不足する実物・運用情報だけを確認する。

| 必要な情報 | 理由・依存する工程 |
| --- | --- |
| 検証に使えるひな形フォームURL | 複製、質問構成、公開方式、回答先タブ生成の実機確認 |
| 検証用の保存先フォルダ | 新規ファイルの作成先。画像からフォルダIDを推測しない |
| 学校ドメイン・回答許可の実際の設定 | 学校外の回答を許可しないこと、本人メール収集を確認する |
| 名簿の参照先とメール・氏名の列名 | 外部名簿／turret生徒一覧のどちらを名前補完に使うか決める |
| タイトル・回答タブのクラス表記 | Classroomの長いクラス名と `1-1` などの短い表記を区別する |
| 資料のタイトル・説明文・必要ならトピック | プレビューできる入力欄を用意。トピックは省略可能にする |
| 実投稿用の検証クラス・対象と実行許可 | 本番生徒へ勝手に試験投稿しないため |

入力の画面・検証・モック試験は、これらの回答を待たずに進められる。外部ファイル作成や投稿など、対象が必要な実機操作だけを保留する。既存の確認用Apps Scriptへの同期許可を、新規フォーム公開・資料投稿・学校の共有権限変更の包括許可と扱わない。
