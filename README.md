# Google Classroom 評価自動送信 GAS

## 成績CSV出力

管理画面の「成績出力」で、対象（既定は全クラス・全期間）、先頭列、授業日列、評価列、並び順を選びます。生徒一覧の対象クラス全員を含め、未回答は空欄、0点は0のまま出力します。名前昇順（数字順対応）・出席番号順・名簿順に対応します。出力シートは作成しません。クラスごとにUTF-8 BOM付きCSVを作り、複数クラスはZIPで取得します。評価は選択列の表示値です。CSVの式として解釈される先頭文字には安全のためアポストロフィを付けます。

生徒一覧は `No / メールアドレス / 出席番号（任意） / 名前 / クラス名 / コースID / studentId / 除外(1)` です。「シートを準備」または再取得で旧6列・7列から移行します。任意の出席番号と除外状態はコースIDとメールで照合して保持します。Noは全体の連番で、出席番号とは別です。転退学者は行を削除する代わりに `除外(1)` に `1` を入力してください。送信・名前補完・成績出力から外し、Classroomから一度消えたりクラスの選択を外した後も除外行を保持します。除外を解除するには同じ行の `1` を空欄に戻します。行削除だけではClassroomに登録が残っていると再取得で戻ります。

クラス取得時はクラス名の昇順（数字順対応）、生徒取得時はクラス別・出席番号順（空欄は名前順、除外者は各クラス末尾）で自動整列します。シート準備・一覧更新時に、未設定なら一覧の全行を対象とするフィルターを用意します。既存のフィルターや絞り込み条件は保持します。手編集後の並べ替えは「クラス一覧」「生徒一覧」の見出しのフィルターから行います。管理画面には整列ボタンを置きません。再取得時はNoを振り直します。コースID＋メールの重複は整列・送信準備・送信で拒否します。回答タブや送信シートには、この整列操作を適用しません。

同じメールの生徒が複数クラスにいる場合は、一方のクラスで除外しても他方へ自動で振り替えません。回答のクラスを対応表で明示してください。

送信準備後に生徒を削除・除外したりstudentIdを変更した場合、送信時の名簿再照合で投稿を止め、送信確認待ちとしてエラーに記録します。戻す場合も宛先と既存投稿を確認してから送信状態を手動で調整してください。成績出力は明示的に除外した生徒の過去回答を今回の出力から外し、元回答・採点結果を保持します。名簿から削除しただけの生徒や未登録者の回答は、引き続き確認事項として出力を止めます。

ICSは任意です。読み込んだ授業名と各クラスを一画面で対応付けます。ICSなしでは回答の授業日を日付順に出力します。ICSありでは回答のない授業日も列に含め、ICSにない日付はクラス単位で「補正」「予定内」「予定外」を選びます。予定内は日付順、予定外は右端です。日付不明も予定外として残せます。回答単位の例外や、実在する別の日付を誤入力した回答も手動修正できます。

日付補正の後に重複を確認します。修正版なら使う回答だけに授業回を割り当て、使わない回答は0（除外）を選びます。別々の授業なら1回目・2回目へ割り当てます。授業回は提出順ではなくクラス共通です。クラス共通の授業回数を手動設定することもできます。新しい回答・判断に関係する内容・基準日程の変更がある場合は再確認します。元回答・採点値・返却の採用判断は変更しません。名簿にない回答や未解決の確認事項がある場合は出力を止め、欠落させません。

ICSは2MB以内の個別VEVENTに対応します。タイムゾーン指定なしは学校の日本時間として扱い、Asia/Tokyo・Japan・UTCも扱います。取消済み予定は除外します。RRULE等の繰り返し指定は未対応のため、各授業を個別予定に展開して書き出してください。基準日程を更新しても、手動の予定内判断は保持します。

下書きは自動保存し、名前付きプリセットは「保存」「別名保存」で確定します。プリセットでは対象クラス・期間を既定で全対象に戻し、「対象クラス・期間も含める」を選べば範囲も保存します。「成績出力」と「設定を保存・出力」の両方で次のJSON（1MiB以内）を入出力できます。

| 種類 | 内容・読み込み時の扱い |
|---|---|
| 【成績出力】すべて | 出力設定・授業日・補正を新しいプリセットとして追加し、下書きに読み込む |
| 【成績出力】並び順＋対応関係 | 列・順序・並び順・クラス対応を置換。既存の補正は保持 |
| 【成績出力】補正ルール | 基準授業日と日付補正・授業回数・採否・先頭列の値の選択を統合。競合は明示選択 |

JSONは内容から自動識別します。名簿・回答・採点結果そのものは含めませんが、個別の判断を再利用するための回答識別情報（クラス・メール等）を含む場合があります。別運用へ移す場合はクラス・列の対応を確認してください。成績は出力のたびに最新のシートから読み直すため、過去の成績の保管には出力済みCSVを利用してください。従来の「全部まとめて（引っ越し用）」は管理・採点・テンプレートの形式を維持し、成績出力は上記3種類で別途書き出します。

保存先は既存の管理用シートです。旧「フォーム管理」は保存・初期化時に「システム管理」へ改名し、既存の履歴を引き継ぎます。両名のシートが存在するときは自動統合せず停止します。通常は直接編集せず画面を使用してください。出力設定は分割保存し、書き込みと読み戻しを確認してから確定します。追加Cloud設定・API有効化・配置ファイルの追加は不要です。

現在のリリース: **v6.2.2**（[リリースノート](docs/releases/v6.2.2.md)）

Google フォーム回答と採点結果から送信データを準備し、Google Classroom の個別メッセージとして生徒へ返却するための Google Apps Script です。複数クラス、複数フォーム用スプレッドシートに対応し、未採点や送信エラーのリマインドメールも送れます。

管理画面から初期設定・データ整理・手動実行・自動実行の時間帯を操作できます。日常処理はトリガーに任せ、設定時は手順に沿って進めます。以下の設定は画面から直接編集できます。

- フォーム側の列名
- `送信シート` の列構成と、旧`評価データ`の移行に使う列名
- 評価値の変換表（段階数・文字列・小数を自由に指定）
- Classroom に送る返信本文テンプレート
- 回答先の自動接続、未採点リマインダー/エラーの通知先メールアドレス
- 自動実行の時間帯と開始・停止

フォーム配付・返却の設定は管理画面で編集し、GAS内部のScriptPropertiesに保存します。採点の表示・入力枠は採点画面で設定します。`Config`・`設定シート`・`設定(編集不可)`は新規作成しません。旧版は管理画面を開いた際、既存値を内部へ移行して読み戻しを確認してから3シートを削除します。移行前の設定シートの明示的な空欄も保持します。移行失敗時は旧シートを残し、再読込で再試行できます。移行後に同名シートを作成・編集しても設定には反映されません。

クラスの選択、生徒一覧の確認、対応表の割当は引き続きシートで行います。Web管理画面の「クラス一覧」「生徒一覧」「対応表」などは、対象タブを直接開くリンクです。設定を別の運用へ引き継ぐには、管理画面の「設定を保存・出力」からJSONを保存・読み込みします。

**設定保存では`送信シート`や旧`評価データ`を削除しません。** 列構成の変更が既存データと合わない場合は保存を止めます。旧データに未移行・準備失敗の行がある間は、移行用の列名も保護対象です。全行が`準備〇`になった旧履歴は、その後の項目変更を妨げません。必要な送信データを退避し、管理画面で対象の行をクリアした後に変更してください。本文だけの変更は既存行を保持します（生成済みの返信本文は自動で書き換えません）。

新規利用は列の対応・取り込み項目・本文が空の状態から始めます。途中まで入力して手順ごとに保存できます。実行や自動実行の開始には必要な設定が揃っている必要があります。旧版で保存済みの設定は引き継ぎます。

1つのGASプロジェクトで1つの運用スプレッドシートを管理します。管理操作は本人限定のWeb管理画面に統一しています。科目や期間を分ける場合は別運用にします。

## 独立した採点画面

スプシのメニュー「自動送信システム → 採点画面を開く」、または管理画面の「採点画面」から開きます。WebアプリURLの末尾を `/exec?page=scoring` にしてブックマークすれば、管理画面を経由せず採点できます。管理画面は `/exec` または `/exec?page=settings` です。各画面から運用スプシへ、採点画面から採点中の回答タブへも移動できます。リンクは別タブで開きます。

採点は scoring_tool の型枠を引き継ぎ、回答表示・得点5枠・講評3枠・自動講評・手修正・キー操作・テンプレパックの入出力に対応します。最初に採点画面の設定で氏名・表示・得点・講評の列とテンプレートを選びます。形式は全クラス共通です。対象はturretに登録した回答シートに限り、管理用・ルール用シートは候補に出しません。採点の列設定と、管理画面の採点済み判定列・返却項目は別設定です。

- 入力・行移動で保持した下書きはブラウザ内に残り、「まとめて保存」または入力停止後の自動保存で回答シートに反映します。保存失敗分は残します。保存中の追加編集も消しません。
- 得点の空欄は既存値を保持し、0点は保存します。講評の空欄は空文字として保存します。列設定を変更した後の古い下書きは、別の列へ誤保存しないよう拒否します。
- ルールの取得中・取得失敗時は講評を消さず、取得できるまでその入力の保存・行移動を待ちます。「再評価」で再試行するか、講評を手入力して保存できます。枠ごとの再評価は、その枠だけを更新します。
- 「採点中」「採点確定」の必須操作はありません。採点保存だけで生徒へ送信せず、既存の採点済み判定セルと日次処理で返却します。保存の一部失敗は再保存が成功するまで返却を保留します。
- 採点設定は `TURRET_SCORING_CONFIG`、テンプレートは運用スプシの **「採点テンプレ」1枚**に保存します。画面とシートの両方から編集できます。採点設定とテンプレパックのJSON入出力は、採点画面と管理画面の両方から同じ処理で行えます。出力はクリップボードへのコピーではなくファイル保存です。旧 `_templates` / `_rules` と旧テンプレパックは使用せず、削除もしません。旧採点設定JSONは引き続き読み込めます。
- 採点画面の「採点テンプレ」、またはスプシの「自動送信システム → 採点テンプレ作成画面へ」で編集します。スプシのメニューは専用Web画面（`/exec?page=templates`）を別タブで開きます。サイドバーは使用しません。新規作成・複製・並べ替え・CSVの貼り付け／ファイル読み込み・検査・試算に対応します。[サンプルテンプレパック](samples/template-pack-bio-basic.json)も利用できます。
- 管理・採点・テンプレ編集の配色は共通です。色は `Setting.html` の `app-theme` にまとめています。配置対象は5ファイルのままです。

### 採点テンプレの書き方

「採点テンプレ」シートは次の13列です。

`テンプレート名 / 枠1 / 枠2 / 枠3 / 枠4 / 枠5 / 出力1 / 出力2 / 出力3 / 出力1を表示 / 出力2を表示 / 出力3を表示 / 使用する`

- 名前は各ルール行に同じものを記入します。編集画面では名前を1回指定し、保存時に各行へ反映します。各列の見出しには書き方のメモがあります。
- 枠の条件は同じ行ですべて満たす必要があります。空欄は条件なし、数値だけなら一致。`>1`、`>=2`、`<3`、`<=2` が使え、`=<` / `=>` も受理します。枠同士の演算やORは使わず、必要な条件を複数行で表します。
- 出力ごとに上から最初に一致した空欄でない文言を採用します。出力が空欄ならその出力だけ次の行へ進み、`0` は文言として出力します。条件が全部空欄の行は常に一致するため、既定の文言は最後の行に置きます。
- 一致するルールがなければその出力は空欄です。採点画面の再評価でも空欄で更新します。入力値が不正、ルール取得失敗などのエラー時は既存の講評を保持します。
- 点数未入力は0とは区別し、数値条件には一致しません。出力には `{枠1}`〜`{枠5}`・`{合計}` を差し込めます。生成後は生徒ごとに手修正できます。
- 「出力1を表示」〜「出力3を表示」は、条件一覧でその行の文言を見せるかだけを指定します。非表示でも講評の生成・保存には使います。「使用する」をオフにすると、その行を判定から除外します。どのフラグも `1`（はい）/`0`（いいえ）、空欄ははいです。
- 条件一覧は元ルールごとに `①:1・②:1：A1 / A2` のようにまとめます。非表示の出力は省略し、出力ごとの採用結果を強調します。出力1と出力2で別のルールが採用されることもあります。

#### 入力できる点数の制限

新規テンプレートは全枠で任意の数値を使えます。必要な枠だけ、編集画面で `1,2,3` などの一覧に制限します。有限の数値であれば0・負数・小数も使用可能です。制限はテンプレート名に紐付けて運用環境の設定へ保存し、13列のシートには書きません。改名・複製は編集画面から行ってください。スプシで直接改名して制限の対応が失われた場合は、元の名前へ戻してから画面で改名します。

**別環境へ持ち出す場合はテンプレパックJSONを使用してください。** version 2のパックにはルール・出力ごとの表示設定・各枠の入力制限をすべて含め、読み込み先で一緒に復元します。シートだけのコピーでは入力制限は移りません。採点設定JSONだけにもテンプレート本体は含まれません。

旧16/17列のシートとversion 1のパックは自動変換しません。旧シートはブックのコピー等でバックアップし、「採点テンプレ」を別名で残してから新しい13列のシートを準備してください。旧パックは原本を保管し、新しい編集画面で内容を確認して作り直します。アプリが旧データを黙って消去することはありません。

#### 表を編集する

条件5列＋出力3列は、セル間にすき間のないグリッドです。選択中は矢印やTabで移動、文字入力で置換、F2・Enter・ダブルクリックで文字編集へ切り替えます。文字編集中の矢印はカーソル移動に使い、講評は改行できます。Shift＋矢印で範囲選択し、表計算からの矩形コピー・貼り付け、消去、元に戻す／やり直しができます。具体的な操作は画面の「？」で確認できます。

既存のCSV取り込みは枠5列＋出力3列の8列です。`枠1,枠2,枠3,枠4,枠5,出力1,出力2,出力3` の見出しは取り込みません。スプシからコピーしたタブ区切り表も使えます。「取り込み内容を確認」→「末尾に追加」→「シートに保存」の順に進みます。CSVファイルは5MB以内、UTF-8 / Shift_JISを選択できます。文言内のカンマ・改行・引用符はCSVの引用符で囲みます。表示設定と入力制限は編集画面で指定します。

「書き方・AIへの依頼文」は現在の入力制限と判定方法を含みます。「依頼内容」「枠と出力の指定」を埋めてAIへ渡してください。

「ルールを検査」で書式・重複等を確認し、「点数を入れて試す」で具体例を試算できます。任意数値を使う場合、意図した採点基準の網羅性までは保証しません。すべての枠を点数一覧に制限した場合は、上限内で組合せによる条件漏れ等も検査します。不正書式は保存できず、意図的な重複などの警告は保存できます。

上限は100テンプレート、各500ルール（表全体2000）、点数一覧は各枠20種類です。有限集合の全組合せが5万件超、または組合せ数×ルール数が500万超の場合は、全件検査を省略したと表示します。保存前にシートまたは入力制限の変更を検知したら上書きせず入力を保持します。スプシ直接編集はGASのロック対象外なので、同時編集は避けてください。

### 同じ授業日の再提出

授業日の列を設定すると、「メールアドレス・クラス・授業日」が同じ回答を重複候補として表示します。送信日が翌日でも検出します。新規ひな形の「授業の日付を入力してください」は自動検出します。既存フォームの別の設問名は、採点設定の「授業日の列」で選択してください。授業日が不要な運用では「重複判定を使わない」を選べます。無効時は画面に明示します。

「重複○件を比較」から答案・提出時刻・評価・返却状態を横並びで確認し、採用する回答にチェックを入れます。3件以上でも比較先を切り替え、比較先の採点へ移動できます。同じ日に別の授業があれば複数回答を採用できます。

採点画面の回答本文の上には、左側の固定幅に `2026/09/29（2日遅れ）` のように授業日と提出状況を表示します。右側の重複・返却状態の開始位置は、日付や遅れ日数によって動きません。遅れの表示と「重複あり」はそれぞれ独立してオレンジ、それ以外の状態文字は黒です。狭い画面ではこの行を横スクロールできます。

日数は、設定した授業日の列と回答シートの「タイムスタンプ」（または `Timestamp`）を、回答シートのタイムゾーンで暦日として比較します。同日は「当日提出」、100日以上は「99日超」、提出日より後の授業日は「授業日前」、授業日が空欄・不正なら「日付不明」、提出日時が確認できなければ「提出日不明」です。日付表示にカーソルを合わせると提出日時と正確な日数を確認できます。入力された授業日は自動補正せず、遅れ日数による返却制限も加えません。授業日の列を無効にした場合も「日付不明」と表示します。

比較用の本文は比較を開いた時に取得します。画面の初期読み込みでは重複件数・返却状態・日付情報を取得し、本文の重複取得を避けて通信量を抑えます。日付表示には取得済みの回答データを使い、追加のフォーム取得やシート読み込みは行いません。比較中に回答が変更された場合は、読み直してから採用してください。採点欄の未反映の下書きは比較へ含まれないため、修正した評価を比較する場合は先に「まとめて保存」してください。

- 未確認の重複は、採用判断まで返却を保留します。選択した授業日が空欄・不正、またはクラスを特定できない回答も保留します。
- 採用しない回答は削除しません。選択を変更したり、判断を保留へ戻したりできます。新しい回答が増えた場合や元回答の内容が変更された場合は、再確認が必要です。
- 返却済みの回答に対して新回答を採用した場合は追加で返却します。以前の投稿は残り、自動削除・更新しません。
- 本文準備済みや旧版で取り込み済みの回答でも、返却前の確認で未判断の重複が見つかれば保留します。生成済み本文や返却済み投稿を、採点の修正だけで自動更新しません。
- 判定は日次処理で回答を読み取った時点の状態です。その読み取り後に届いた再提出まで、同じ実行で検出できる保証はありません。

内部の採用判断と採点保存の完了状態は、各回答タブの `管理` 列にまとめて保持します。右端の順序は `管理` → `送信状態`（設定した列名）です。追加は管理用の1列だけで、`_scoring_decisions` / `_scoring_saves` は新規作成しません。未保存の採点入力そのものを保存する列ではありません。

旧2シートがある場合は「必要なシートを準備」で管理列へ移行し、全記録の移行先と保存結果を確認してから削除します。移行先がない・保存を確認できない場合は旧シートを保持して停止します。管理列の値と見出しのメモはシステム専用のため、手動で削除・編集しないでください。回答は従来どおり行番号で識別するため、回答タブの物理的な行並べ替え・行削除は行わないでください。旧単独版の未保存下書きは移行しません。旧画面でシートへの保存を完了してから切り替えます。

## Web管理画面とフォーム配布

既存のturretでは、スプシの「自動送信システム → 管理画面を開く」を実行し、Apps Scriptの「デプロイ → 新しいデプロイ → ウェブアプリ」で**実行ユーザーを自分、アクセスできるユーザーを自分のみ**にします。デプロイ画面に表示されたWebアプリURLを一度開くと、そのURLを内部に記録します。以降はスプシのメニューから開けます。Web画面はデプロイした本人の管理用です。学校の生徒へ渡すのはフォームの回答URLです。

独立したGASへ5ファイルを配置してWebデプロイする場合、初回画面から空の運用スプシを作成できます。この方式では期間ごとに別GASを用意して設定JSONを再利用します。紐付きスプシの方式では「管理 → 次の期間用に複製」でクラス・生徒だけを残した複製を作り、設定JSONを出力します。旧フォームの接続先は空にし、通知先・項目・本文・希望時刻をJSONに含めます。複製先の管理画面でJSONを読み込み、生徒一覧を再取得してからWebデプロイと自動実行を設定してください。元データは保持します。設定プロパティのコピーに依存しないため、スプシを手動コピーした場合もJSONを読み込んでください。

「設定」のセットアップガイドを上から順に進めます：

1. **シートを準備**：「必要なシートを準備」でクラス一覧・生徒一覧・採点テンプレ・対応表・送信シート・エラー・システム管理を作成（既存データは保持）。保存済みの設定JSONがあれば読み込む。
2. **クラスと生徒**：クラス一覧を取得し、同期対象に1を入れ、生徒一覧を取得する。
3. **フォームを準備**：ひな形の編集URLを入力するか「ひな形フォームを新規作成」で作成する。新規ひな形は必須・年付きの日付項目「授業の日付を入力してください」を含み、turretのスプシと同じフォルダに配置され、編集URLが自動入力される。日付は回答日ではなく対象の授業日を入力する。「ひな形を編集」からその他の設問を追加し、メール収集を必ず「確認済み」に設定する。その後、保存先フォルダ・フォーム名・回答許可先・クラス表記を入力して作成する。投稿タイトル・投稿文は後の「資料を投稿」で設定する。評価・コメント列は作成後に次の手順で追加する。クラス別フォームは非公開で準備し、この運用スプシに回答タブを作成。参照元と対応表も自動登録する。回答タブの先頭文字は「フォーム回答」で自動設定され、入力は不要。既存の接続設定は保持する。
4. **評価・コメント列**：準備した回答タブを選び、必要な評価・コメント列を追加する。新しい列は自由入力とする。
5. **回答先と通知先**：回答先URLと対象タブの先頭文字は自動登録するため入力不要。「未採点リマインダー/エラーの通知先メールアドレス」を登録するか、「メール通知を利用しないことを確認しました」にチェックし、保存してから設定済みになる。説明の「？」で用途を確認できる。下の「回答シートとクラスの対応表」は必要に応じて作成／修正する。
6. **列と項目**：メール・氏名・採点済み判定の列をプルダウンで選び、各列のメッセージへの取り込みルール・任意の評価変換を設定する。
7. **メッセージ**：返却本文を設定する。入力や差し込み候補の挿入に合わせて、架空データの仕上がりが自動更新される。未保存の取り込み・変換ルールも反映し、保存・送信は行わない。通信に失敗したら「プレビューを更新」で再試行する。
8. **資料を投稿**：最初から開いている「一括設定」で投稿タイトル・投稿文を入力し、「各クラスに反映」で保存する。初期値をそのまま使う新規フォームも登録が必要。「一括投稿（今すぐ・○クラス）」は未投稿の資料を対象に、文面とクラスを確認してClassroomの「授業」へ投稿する。予約済み・投稿済み・削除済みは対象外。公開予約と受付終了日時は、同じ枠の日時欄と「保存」で一括登録できる。例外は各フォームの「個別登録」の折り畳みから設定し、投稿済み・予約済みの登録ボタンは「反映」と表示する。個別の投稿・受付開始／停止・予約取消・ひな形から更新・照合・削除は「個別操作」のプルダウンで選び「実行」する。文面の未保存中は投稿・予約を無効にし、保存後も開閉状態と入力中の日時を保持する。

   一括登録は投稿済み・予約済みの資料にも文面を反映します。個別の文面も置き換わるため、クラスごとの例外は一括反映後に設定してください。「個別設定あり」は登録した共通文面と異なる入力を示し、保存状況は開いた欄の「保存済み／未保存」で確認できます。共通文面の基準は各フォームの管理記録に保存するので、画面を開き直しても個別設定の印を維持します。旧記録は初回の一括登録時に基準を追加します。一括処理で一部が失敗した場合は成功分を保持し、失敗したクラスの入力と理由を表示します。再試行では反映済み・投稿済みのクラスを除外します。

9. **自動実行**：日本時間の時間帯と診断結果を確認し、明示的に開始する。フォーム作成や資料投稿だけでは自動返却を開始しない。

### 一部のフォーム作成に失敗した場合

「フォームを準備」の「準備したフォーム」一覧から、失敗したクラスだけを再開できます。「準備を続ける」が表示されている場合は、そのボタンを押します。

下の「作成内容を確認」を再度押す方法でも、準備済みのクラスをスキップして、未作成・準備途中のクラスだけを準備できます。確認画面に「新規作成」「準備を再開」「照合して再開」「再作成」「スキップ（準備済み）」を表示します。すべて準備済みなら新たに作成せず、その旨を表示します。同じクラス・回答タブの管理履歴を再利用し、既存フォームの個別設定は保持します。途中のフォームは保存済みの設定で再開し、新規作成分だけ入力中の設定を使います。管理履歴のない同名タブ、別クラスのタブ、複数の作成履歴がある場合は自動で上書き・統合しません。

「作成結果の確認待ち」の場合は「作成結果を照合」を押します。作成済みフォームが1件見つかれば、そのフォームを使って「準備を続ける」で再開できます。見つからない場合は、少し待ってもう一度照合してください。前回の作成処理が終了し、Driveの保存先フォルダにも対象のフォームがないことを確認できた場合は、表示された「このフォームだけ再作成」、または「作成内容を確認」の再作成対象を確認して準備します。保存済みの設定と同じ作成履歴を使い、成功したクラスには影響しません。

再作成の直前にも照合し、フォームが見つかれば既存のものを使います。複数件が見つかった場合や、検索の未完了・権限エラーなどで判断できない場合は再作成しません。全クラスの新規作成や作成履歴の手動削除でやり直さないでください。

### 資料の投稿予約とフォームの受付終了

「資料を投稿」の各フォームで、投稿設定を保存した後、即時投稿に加えて「資料の投稿予約」から公開日時を日本時間で指定できます。予約登録時点でフォームは公開・受付中になり、Classroomの資料だけが指定日時に公開されます。公開前でもURLを知る許可済みユーザーは回答できます。

- 予約日時の変更と取消に対応します。取消は資料を下書きとして保持し、フォーム受付や受付終了予約は変更しません。下書きは即時投稿・再予約できます。
- 「予約済み」と「投稿済み」を区別します。表示は最終確認時の記録です。「投稿状態を確認」でClassroomの現在状態を取得し、時刻が過ぎただけでは投稿済みにしません。
- Classroomの資料公開は、予定時刻から最大5分ほど遅れる場合があります（[Google公式の案内](https://support.google.com/edu/classroom/answer/9123621?hl=ja)）。公開予定と受付終了の間には、回答時間に加えて余裕を設けてください。
- 作成・変更の結果が不明な場合は「投稿結果を照合」を使います。自動で同じ資料を作り直しません。公開済み資料を予約取消で非公開へ戻すことはできません。
- 「フォームの受付終了予約」で終了日時を設定・変更・取消できます。資料公開予定より後の日時を指定してください。予約日時はシステム管理の記録に保存し、設定JSONの出力・次期間への複製には含めません。
- 終了予約はGASの専用タイマー1個で約5分間隔に確認します。処理の遅延や失敗により停止が遅れる場合があるため、秒・分単位で厳密な試験終了を保証する用途には使わないでください。失敗は一覧へ表示し、次回に再試行します。
- 終了予約の設定・取消だけではフォームの受付状態を変更しません。期限後に再開するには、先に終了予約を変更・取消し、「受付開始」を実行します。フォーム更新によって期限後の受付が再開されることもありません。
- 「複数クラスの日時をまとめて指定」では、未投稿資料の予約と準備済みフォームの受付終了を一括設定できます。クラスごとの成功・失敗を表示します。資料予約の再実行は成功済みの予約を対象にしません。

受付終了は既存回答・採点・返却を削除せず、日次返却の開始・停止から独立しています。予約タイマーが見つからない場合は、設定した管理者で「タイマーを修復」を実行してください。予約がなくても共通タイマーは残りますが、期限を過ぎた未処理フォームがなければフォームを変更しません。

追加のCloudプロジェクトやCloud Schedulerは不要です。Googleフォーム本体の標準終了日時とturretの終了予約は別管理なので、同じフォームではどちらを使うか統一してください。

クラス別フォーム用の保存先フォルダ欄は従来どおり手入力で、ひな形の保存先とは独立しています。回答許可先は学校メールの `@` より後ろのドメイン、または明示的に許可するメールを指定します。個人テストではメールを指定してください。誰でも回答できる設定や、確認できないグループ権限では公開しません。

準備と投稿の進捗は保存された管理記録から表示します。投稿済み表示は記録時点の状態です。対応表の進捗は「回答先と通知先」に集約し、「クラスと生徒」の完了表示とは分離しています。既存フォームで運用する場合に、turretによるフォーム作成・資料投稿を強制することはありません。

「一括設定」では、投稿タイトル・投稿文・トピックを「各クラスに反映」で保存します。資料の公開日時とフォームの受付終了日時の「保存」は、それぞれの日時だけを登録し、他の欄の入力は保存しません。「一括投稿」の左にある「一括登録」は、文面・トピックと入力済みの日時を一度の確認でまとめて登録します。日時の空欄は変更せず、即時投稿もしません。既存の受付終了日時が新しい公開日時を妨げる場合は、確認に表示した順番で先に終了日時を延長します。途中の失敗時は成功済みの登録を保持し、後続の項目は実行しません。日付は入力欄の補助表示・一覧・確認画面とも日本時間の曜日付きです。

トピック候補は「クラス一覧」で最初に選択されたクラスから取得します。「トピックを変更する」は初期状態ではオフで、タイトル・投稿文だけの保存ではClassroomで手動設定したトピックも保持します。トピックを設定・変更するときだけチェックしてください。チェックした状態で先頭の空欄を保存すると、投稿済み資料のトピックを解除します。チェックせずに空欄を保存しても解除しません。ほかのクラスでは同名のトピックを各クラスのIDへ対応させます。同名がないクラスは確認画面にまとめて表示し、承認後に作成して反映します。キャンセルでは作成しません。同名の重複や取得失敗は停止して確認を求めます。作成結果が不明な場合は再作成せず、「設定の更新を再開」で一覧と照合します。v6.2.0で途中になった設定更新は、トピックを現在の状態のまま保持して他の項目だけ再開します。必要なトピック変更は再開後にチェックして保存し直してください。一覧に現れない場合はClassroomで確認してください。

トピック対応には manifest の `classroom.topics` 権限を使用します。更新後の初回利用時に通常のGoogle再承認が必要になる場合があります。既存のClassroom高度なサービスを使うため、新規Cloudプロジェクトや追加APIの有効化は不要です。配置対象は従来の5ファイルです。クラスごとの例外は「個別登録」で編集します。一括入力欄も画面移動・状態更新で保持します。狭い画面では縦1列に表示します。

投稿設定の下書きは画面移動・状態更新でも保持します。保存に失敗した場合は投稿できず、途中の更新は「設定の更新を再開」で完了してください。「保存済み設定を読み込む」で未保存の文面を取り消せます。投稿済み・予約済みの資料で保存すると、同じ投稿IDのタイトル・本文だけを更新し、公開状態・予約日時・回答・採点結果は保持します。従来の準備画面で保存済みの投稿設定はそのまま利用でき、旧画面・旧記録の形式も維持します。

フォームの準備は2段階です。「フォームを準備」でクラス別フォームを作り、この運用スプシへ回答先を接続します。この段階では名前補完・管理・送信状態など必要な列だけを自動作成します。続いて「評価・コメント列」で作成済みの回答タブを選び、必要な採点項目やコメント欄を追加します。複数クラスの回答タブへまとめて適用できます。

作成済みフォームの一部を変更するときは、「フォームを準備」の一覧の「設定を編集」を押します。保存済みのフォーム名・回答許可先・クラスの短い表記を読み込み、変更した項目だけを保存できます。適用するフォームを複数選ぶと、その項目だけをまとめて反映し、各クラスの他の設定は保持します。「資料を投稿」にはフォーム設定の編集ボタン・編集欄はありません。投稿タイトル・投稿文は「資料を投稿」の各フォームで保存します。投稿済み・予約済み資料も同じ投稿IDのまま更新し、公開状態・予約日時・回答・採点結果は保持します。画面を開き直した際の新規作成欄には直近の保存済み設定を初期表示します。同じ画面で新しい保存内容を使って作成する場合は「保存済み設定を読み込む」を押します。入力中の新規作成設定は、確認するまで置き換えません。

クラスの短い表記の変更はフォーム名と資料タイトルへ反映します。回答タブ名は返却履歴との対応を保持するため変更しません。ひな形・保存先・メール列・名前列は作成時の設定として表示します。設問はひな形を編集して「ひな形から更新」、評価・コメント列は専用の手順で追加してください。回答許可先の変更はクラスの生徒全員が含まれることを確認し、受付を一時停止して適用します。完了後は元の受付状態へ戻しますが、受付終了日時を過ぎている場合は再開しません。途中で失敗した場合は一覧の「設定の更新を再開」で続けます。編集中に別の画面で設定が変更された場合は、編集を開き直してから再確認してください。

追加列の入力は空から始め、「＋ 列を追加」で増やします。画面上部と対象の回答タブ一覧には、保存済みの評価・コメント列名を表示します。回答タブを選び、追加欄が空のまま「列の設定内容を確認」を押すと、最新の保存済み設定を取得して列名を確認できます。この確認では列や設定を変更しません。未設定のタブには列を追加する操作を案内します。追加方法の説明は「追加する列」の「？」で確認できます。スプレッドシートで手動変更した列の状態は、回答タブで確認してください。

上下ボタンは入力中の列名を移動します。新しい列は入力順に追加し、同名の既存列は再利用します。既存列の値・数式・メモと、今回指定しなかった列は保持します。入力欄から列を削除しても、回答タブの既存列は削除しません。新しい列は自由入力で、数値の範囲や選択肢は設定しません。同名の既存列を使う場合、入力規則も保持します。必要な評価変換は「列と項目」で設定します。追加列は「列と項目」に文字項目として登録し、同じ参照列の既存項目・差し込み名・評価変換は保持します。必要なら登録後に差し込み名や変換を変更してください。

`管理`と送信状態はシステム専用列で、通常の画面から列名を変更できません。既存設定で別名の送信状態列を使用している場合は、その名前を維持します。列追加後は管理・送信状態を右端に配置します。スプレッドシート側でも、これらの見出しを変更・削除しないでください。

採点済み判定は「列と項目」の既存設定を使い、フォーム作成時には変更しません。未設定なら、送信準備・自動実行の前に設定してください。追加列なしでもフォーム作成は可能です。クラスが未選択の場合は理由と「クラスを選択する」を表示し、作成を無効にします。

「評価・コメント列」はturretで作成・接続した回答タブが対象です。既存フォームを手動で接続した回答タブの列は、スプレッドシートで追加してください。運用内の取り込み設定は共通なので、対象の回答タブには設定で必要な列をそろえてください。送信データや旧評価データが存在し、項目の追加によって列構成が変わる場合は、列追加前に停止して既存データを保護します。確認後に設定や見出しが変わった場合も適用を停止します。一部の対象だけ失敗した場合は件数と理由を表示し、途中の設定は「列の設定を再開」で続けられます。設定が途中の間は採点保存・返却処理と対象フォームの更新を停止します。

フォーム名・資料タイトルでは `{class_label}` が「フォームを準備」の「クラスの表記」で指定した読み方（未入力ならClassroomのクラス名）に置き換わります。旧 `{class}` も使用できます。返信本文の `{class_name}` はClassroomのクラス名を指します。

ひな形の新規作成は、クラス未選択・他の設定が未保存でも利用できます。既存URLの置き換えには確認を表示し、元のフォームは残します。同じ画面で通信失敗後に再試行しても二重作成しません。結果不明の場合はマイドライブの「turret ひな形」を確認し、作成済みの編集URLを入力してください。ひな形の作成だけでは、クラス用フォームの複製・回答先の接続・資料投稿は行いません。

スプレッドシートがマイドライブ直下にある場合は、ひな形も直下になります。保存先フォルダを取得できない場合は作成前に停止します。作成後の配置に失敗した場合は、フォルダのアクセス権を確認して同じ画面で再試行してください。作成済みフォームを使って配置を再開します。以前作成したひな形は自動移動しません。

回答許可のドメイン欄はドメイン単位の指定です。Googleフォームに表示される組織名や「対象ユーザー」の名前を解決する機能ではありません。組織の共有設定と同じ範囲になるかは、実際のドメイン・対象ユーザー設定を確認してください。

名前はClassroom生徒一覧からコースIDとメールで照合します。フォーム準備時に登録される回答トリガーで、新しい回答の名前を自動補完します（生徒一覧への登録と、トリガーの正常動作が必要）。「名前を反映」を一度押すことで自動補完が有効になるわけではありません。送信準備前の補完に加え、採点画面上部の「採点テンプレ」の右側に手動の「名前を反映」を用意しています。読み込み済みの回答シート全体が対象で、turretで管理しているフォームの回答シートで利用できます。「資料を投稿」には補完ボタンはありません。補完後は名前を再読み込みし、採点中の入力は下書きとして保持します。未登録・同じメールの氏名競合では名前を空欄のまま残し、既存の名前・採点・コメントを上書きしません。名前のセルに数式がある場合も、表示が空欄でも補完対象から除外します。未照合が残る場合は管理画面で生徒一覧を更新し、採点画面から再実行してください。フォーム受付停止と返却処理の停止は別です。

### 投稿を削除する

turretがIDを記録した資料は「設定 → 資料を投稿」、個別返却投稿は「管理 → 個別返却の投稿を管理」から削除できます。本文・投稿ID・日時を確認して実行します。フォーム・回答・採点・送信済み状態は保持し、返却の削除を理由に自動再送しません。資料は削除後に明示的な再投稿が可能です。過去版のID不明の投稿や、別プロジェクトが作った投稿は対象外です。

外部操作の結果が不明な場合は確認待ちとして記録し、自動で二重作成・再投稿しません。「作成結果を照合」「投稿結果を照合」で確認します。一意に照合できない場合や権限喪失・削除済みでAPIが取得できない場合は、Drive／Classroom上での確認が必要です。履歴の書込に失敗した返却は「送信確認待ち」で止まり、エラー記録の投稿IDから確認できます。

追加サービスはDrive API v3です。フォーム操作にはGAS標準のFormAppを使うため、Google Forms APIの有効化や標準Cloudプロジェクトの新規作成は不要です。初回にForms・Driveの権限を承認してください。FormAppではメール収集方式の「確認済み」を指定・判定できません。ひな形のメール収集方式はフォーム画面で一度「確認済み」に設定し、管理画面の確認欄にチェックします。新規ひな形の作成だけでは、この設定は完了しません。[具体的な導入・検証手順](docs/development.md#web管理画面の導入2026-09-29)を参照してください。

フォーム操作で権限不足になる場合は、Apps Scriptエディタから `authorizeFormIntegration` を実行し、不足している権限を承認してください。この関数は認証確認だけを行い、フォームや投稿は作成しません。

「資料を投稿」の「ひな形から更新」で配付済みフォームを更新できます。回答列を質問順へ整理し、削除済み質問の回答がある列は後方へ保存、空列のみ削除します。管理列がある場合は、保存した旧回答列より後ろの最終2列を `管理` → `送信状態` とします。管理列をまだ追加していない旧回答タブでは従来どおり旧回答列が右端です。採点用のテスト形式・動画・ファイルアップロードを含むフォームや画像の追加・差し替えは自動更新の対象外です。初回の複製・配付は利用できます。更新の対応範囲と検証結果は[フォーム更新の記録](docs/reports/2026-09-29-form-updates.md)を参照してください。

専用テスト環境の準備状況とChromeでの通し確認は[テスト手順](docs/testing.md)を参照してください。

- 同期対象クラスの生徒一覧を一括取得

- 運用スプシ内・外部スプシの複数の回答シートから採点済みデータを読み取り
- 送信先クラス・生徒情報をひも付け、評価変換と本文作成をまとめて実行

## 全体フロー

通常の返却は **回答・採点シート → 送信データの準備 → `送信シート` → Classroom送信** です。準備時に必要項目の抽出・評価変換・宛先の照合・返信本文の作成を行い、`送信シート`へ保存します。通常処理では`評価データ`を作成・追記しません。外部スプシを参照元にする既存の運用も引き続き使えます。

手動実行は「送信データを準備」と「生徒に送信」の2段階です。準備だけでは投稿せず、送信時は保存済みの本文を使います。準備後に採点・評価変換表・テンプレートを変更しても、作成済み本文は自動で更新しません。

管理画面は、上記「Web管理画面とフォーム配布」の8ステップです。既存フォームを利用する場合も、回答先・列の用途・本文を確認してから自動実行を開始します。

「シートを準備」の「必要なシートを準備」で、クラス一覧・生徒一覧・採点テンプレ・対応表・送信シート・エラー・システム管理の7シートを作成します。列設定前でも送信シートを作成でき、空の見出しは次の準備時に保存済みの設定へ合わせます。繰り返し実行しても既存行は消しません。送信データが入ったシートの列構成が設定と合わない場合は、上書きせず停止します。

上部の「設定を保存・出力」から、フォーム・列と項目・本文の変更をまとめて保存し、JSONを書き出し／読み込みできます。自動実行の時間変更は下書きを保持し、自動実行画面で別途確定します。設定保存やJSON適用だけでは自動実行は始まりません。

上部メニュー・セットアップガイド・下部の保存状態は固定し、入力部分だけスクロールします。回答先URLとシート名の接頭文字の入力欄はありません。通知先は1件1行で表示し、複数件は追加できます。管理・手動実行は操作と件数を一覧にまとめ、原因や履歴などの詳細を開いて確認します。狭い画面では手順一覧を横にスクロールできます。

「フォームを準備」「資料を投稿」と「管理」は押すと直ちに切り替わり、前回取得した内容を表示しながら最新情報を取得します。初回は取得中の案内を表示します。失敗時は再取得でき、入力中の値は保持します。更新中のタブ移動は可能ですが、保存・投稿などの処理は読み込み完了を待って実行します。

Web管理画面の「管理」→「シートを確認・編集」は、「スプレッドシートを開く」から直接別タブで開きます。

管理画面は実際のシートと設定から進捗を判定します。再訪時は必要な手順へ直接移動できます。シート編集後は再読込してください。別操作で設定が変わっていた場合、古い画面からの保存は拒否します。未保存の画面入力は手順の切替・再読込で保持し、閉じる前に確認します。

## 管理用スプレッドシートの構成

この GAS は、以下のシート名を前提に動作します。

### 設定の保存先（シートなし）

列の用途・取り込み項目・評価変換・本文・フォームURL・通知先などは、内部の`APP_CONFIG`に保持し、同じ保存内容を`APP_CONFIG_BACKUP`にも保持します。保存は読み戻しを確認し、失敗時は以前の値への復元を試みます。自動実行の希望時刻・トリガー管理情報も従来どおり内部保存です。

初期準備では`クラス一覧`・`生徒一覧`・`採点テンプレ`・`対応表`・`送信シート`・`エラー`・`システム管理`を作成します。回答・送信・システム管理などの業務データは引き続きシートに置きます。旧`評価データ`があれば、移行用に保持します。

### `クラス一覧`

管理画面のクラス一覧取得で生成・更新されます。すべてのページの取得成功後にクラス名の数字順で置換し、コースIDが同じクラスの同期対象は維持します。

| 列名 | 内容 |
| --- | --- |
| クラス名 | Google Classroom のコース名 |
| コースID | Google Classroom のコース ID |
| 同期対象(1) | 生徒一覧同期の対象にするクラスは `1` |

### `生徒一覧`

管理画面の生徒取得で生成・更新されます。全対象クラスの取得に成功するまで既存一覧を保持します。対象クラスを変えたら再取得してください。

| 列名 | 内容 |
| --- | --- |
| No | 連番 |
| メールアドレス | 生徒メール |
| 出席番号（任意） | 任意入力。生徒一覧の再取得でもクラス・メールを照合して保持 |
| 名前 | 生徒名 |
| クラス名 | 所属クラス名 |
| コースID | 投稿先コース ID |
| studentId | Classroom の生徒 ID |
| 除外(1) | 転退学等で対象から外す生徒は `1`。再取得後も保持。解除は空欄 |

### `対応表`

管理画面の対応表作成で生成・更新されます。既存の`クラス名`と`メモ`は、同じ`元SS_ID`と`元シート名`の組み合わせであれば再生成時に引き継がれます。

| 列名 | 内容 |
| --- | --- |
| 元SS_ID | フォーム回答元スプレッドシート ID |
| 元スプシ名 | フォーム回答元スプレッドシート名 |
| 元シート名 | フォーム回答元シート名 |
| クラス名 | `クラス一覧` の同期対象クラスから選ぶ |
| courseId | `クラス名` から自動入力される Classroom コース ID |
| メモ | 任意のメモ |

同じメールアドレスの生徒が複数クラスにいる場合は、送信データを準備する前に `対応表` で `元SS_ID + 元シート名` とクラスを対応づけてください。

### 旧`評価データ`の引き継ぎ

旧版で作成したシートがある場合だけ使用します。新規作成・追記・自動削除は行いません。送信準備では、このシートの処理状態が空欄の行を先に移行し、同じ元回答を現在の回答シートから重ねて追加しません。

移行する項目値は、旧シートに保存済みの変換後の値を優先します。変換表や元回答が後から変わっていても、保存済みの評価値を現在の表で再変換しません。本文は移行時のテンプレートで作成します。`準備〇`・`準備×`など処理済みの旧行は自動で再処理しません。移行後も旧行は残し、状態を記録します。

固定列:

- `元SS_ID`
- `元シート名`
- `元行番号`
- `メールアドレス`
- `名前`
- `処理状態`

この後ろに、旧版で設定した取り込み項目の列があります。移行が完了するまで列名や元回答情報を変更しないでください。

### `送信シート`

「必要なシートを準備」で作られます。宛先・返信本文・元回答の情報・送信状態を保存します。列構成は保存済み設定に従います。

固定列:

- `元SS_ID`
- `元シート名`
- `元行番号`
- `No`
- `メールアドレス`
- `名前`
- `クラス名`
- `コースID`
- `studentId`
- `送信状態`
- `返信本文`（固定）

本文の保存列名は管理画面から変更できません。以前の設定に別名が保存されている場合は、既存データを守るためその名前を維持します。設定JSONの旧形式も引き続き読み込めます。

必要に応じて、その後ろに送信用の追加列が並びます。

### `エラー`

送信失敗やフォーム状態更新失敗時に自動生成されます。

| 列名 |
| --- |
| タイムスタンプ |
| シート名 |
| 行番号 |
| メールアドレス |
| 送信状態 |
| エラー種別 |
| エラーメッセージ |

## フォーム回答スプレッドシート側の前提

フォーム準備時に、この運用スプレッドシートと回答タブの接頭文字 `フォーム回答` を自動登録し、対象タブを読み込みます。既存の接続URL・接頭文字の設定も引き続き利用します。

回答先URLと接頭文字を管理画面で編集する必要はありません。旧設定JSONの接続情報は従来どおり読み込みできます。

各対象シートには、少なくとも次の列が必要です。

- メール列
- 名前列
- 送信状態列
- Web管理画面で定義した各取り込み項目の元列

ヘッダ名は設定値との完全一致で検索されます。フォーム側の設問名を変えた場合は、先にWeb管理画面の内容も更新してください。

`管理` 列は、新規フォームの回答準備時、既存回答への採点保存・重複判断時、または旧記録の移行時に自動追加します。既存の送信状態列も右端へ移動します。`管理` は予約名のため、設問・採点の出力先・返却本文の取り込み項目には使えません。

## 画面の説明

各画面の丸囲みの「？」は、カーソルを合わせるかキーボードでフォーカスすると説明を表示します。離れると閉じ、クリック・タップで固定、もう一度押すと解除します。Escや外側のクリックでも閉じられます。管理画面・採点画面・採点テンプレ作成画面で共通です。テンプレ作成画面の「書き方・AIへの依頼文」は、説明をコピーするための画面を開きます。

## 送信内容

Google Classroom には、Web管理画面で設定したテンプレートを元に各生徒向けの本文を投稿します。

`{score}` のように書くと差し込みに変換されます。既存の `＜score＞`・`<score>`・`{{score}}` と条件付きセクションも引き続き使えます。保存済みの本文や設定JSONは自動で書き換えません。
`({score})` のように書けば、括弧付きのまま `(A)` のように表示できます。
値だけを書く行は、その値が空なら行ごと非表示になります。  
見出し付きの行も、対応する値が空ならその行ごと自動で消えます。

固定トークン:

- `{student_name}`
- `{class_name}`
- `{course_id}`
- `{row_no}`

新規設定では取り込み項目と本文は空です。差し込み候補は項目と意味を1行で表示し、詳細から参照列と例を確認できます。以前の評価返却形式は[設定例JSON](examples/profiles/assessment.json)から読み込めます。読み込みは任意です。

### 評価の変換表

「列と項目」の列名候補は画面を開くと自動取得し、再取得もできます。列の役割はPCで3列に並び、各項目の回答シートの列名もプルダウンから選択します。保存済み・編集中の選択値は候補に保持し、管理・送信状態は候補から除外します。

「各列のメッセージへの取り込みルール」の各評価項目で、変換元と本文に使う値を追加・削除できます。文字項目は値をそのまま使い、評価への変換は任意です。同じ`1・2・3`を、ある項目では`×・△・○`、別の項目では`C・B・A`に変換できます。項目別の`gradeScale`を指定しない既存項目は、共通設定`config.gradeScale`を引き継ぎます。段階数は固定ではなく、`4.5 → 優`、`合格 → よくできました`のような小数・文字列も登録できます。

前後の空白を除いて照合し、十進数の`5`・`05`・`+5.0`は同じ変換元として扱います。同じ値を重複登録することはできません。表にない値は元の値を保持します。新規設定の表は空で、空のまま下書き保存もできますが、`score_grade`の項目を使って処理を実行するには変換表が必要です。変換しない場合は、その項目を「文字（そのまま）」に変更してください。

旧設定の評価変換を引き継ぐ場合の対応は次のとおりです。

| 数値 | 変換後 |
| --- | --- |
| 5 | A |
| 4 | B+ |
| 3 | B |
| 2 | B- |
| 1 | C |

変換表の変更は、今後新たに回答から準備する送信データに適用します。旧`評価データ`から移行する保存済みの値や、生成済みの`送信シート`の本文は自動で再変換しません。過去の行に変更を適用したい場合は、送信済みかを確認してから対象を整理してください。設定変更だけを理由に既存データをクリアしないでください。

## 送信前の診断

「自動実行を設定」と「手動実行」にある「保存済み設定で診断する」から実行します。未保存の入力は先に保存してください。設定・参照元への接続・必要な列・名簿と対応表による宛先・本文を、読み取り専用で確認します。シートへの書き込み、Classroomへの投稿、通知メールの送信は行いません。

対象は、未送信の送信シート、移行待ちの旧評価データ、未準備の採点済み回答です。最大500候補・合計5,000データ行まで確認し、実データの宛先・本文を最大10例表示します。送信待ちの行は保存済み本文、未準備の回答は現在の設定による確認用本文を表示します。旧データの移行候補は保存済みの変換後の値を優先して本文を確認します。上限に達した場合は未確認のデータが残っていることを表示します。

診断結果は、その時点で確認した範囲に限ります。**Classroomの投稿権限は検証しないため、診断成功は実送信の成功保証ではありません。** 設定やデータを変更したら再診断してください。設定保存・状態更新後は、前の診断結果を破棄します。

## 状態管理

採点済み判定:

- Web管理画面で指定した「採点済み判定に使うフォーム側ヘッダ」に値が入っている行を採点済みとして扱います

未採点判定:

- `メール列名` に値があり、かつ採点済み判定に使う列が空の行を未採点として扱います

### フォーム回答シートの `送信状態`

| 状態 | 意味 |
| --- | --- |
| 空欄 | 未処理 |
| `反映〇` | 旧版で`評価データ`に取り込み済み。旧データから送信準備へ引き継ぐ |
| `準備〇` | `送信シート` まで生成済み |
| `準備×` | メール不明、生徒一覧未登録などで送信不可 |
| `済` | Classroom 送信済み |
| `送信エラー` | Classroom 側で致命的エラー |

### 旧`評価データ` の `処理状態`

| 状態 | 意味 |
| --- | --- |
| 空欄 | 移行待ち |
| `準備〇` | `送信シート` 生成済み |
| `準備×` | 送信不可。自動では再処理しない |

### `送信シート` の `送信状態`

| 状態 | 意味 |
| --- | --- |
| 空欄 | 未送信 |
| `未` | 明確なレート制限による投稿拒否。再送対象 |
| `済` | 送信成功 |
| `エラー` | 致命的エラー |
| `送信確認待ち` | 投稿結果・状態記録が不明、または同じ元回答の送信行が重複。自動再送しない |

送信処理中も、投稿直前から結果の記録まで一時的に`送信確認待ち`になります。処理終了後も残っている行を確認してください。

クリアと手動送信は対象件数を確認して実行します。確認後にデータが変わった場合は、再読込して再確認する必要があります。

## 推奨トリガー運用

管理画面の自動実行で、毎日の時間帯を変更できます。初期値は次のとおりです。

- 5〜6時: 回答・採点結果から送信データを準備し、返信本文まで保存
- 8〜9時: 保存済みの送信データをClassroomへ送信
- 16〜17時: リマインダー（任意。初期状態は無効、通知先が必要）

時刻はAsia/Tokyoです。送信準備→送信→リマインダーの順に異なる時間帯を指定します。Googleの時間トリガーは時台指定のため、分単位の定刻を保証しません。[Googleの仕様](https://developers.google.com/apps-script/guides/triggers/installable)

旧版から保存済みの時間帯は引き継ぎます。従来の「取り込み」の時間帯で本文まで作成するため、準備から送信までの間に行った採点・テンプレートの変更は、その保存済み本文に反映されません。送信の時間帯には新しい本文を準備しないため、準備後に採点した回答は次回の準備対象です。必要なら手動で送信データを準備してください。設定JSONの`importHour`・`deliveryHour`と既存のトリガー関数名は互換性のため保持します。

管理画面で設定済みの日次トリガーは、今回のコード更新に伴う作り直しは不要です。準備時刻に準備のみ、送信時刻に送信のみを実行します。

開始・変更・停止は明示操作です。初めて使うときはGoogleの追加権限承認が必要になる場合があります。旧版の4処理や`prepareSendData`をApps Script側で直接登録した時間トリガーが見つかった場合は、置換対象を確認して切り替えます。他用途のトリガーは変更しません。旧トリガーの一部削除だけが成功した場合、元の時間帯はAPIで復元できないため、残ったトリガーを確認して再実行してください。

管理者は最初に開始した1アカウントです。停止後も同じ管理者アカウントで変更します。他アカウントが作った旧トリガーは表示・停止できないため、各作成者がApps Script側で停止してください。管理用トリガーは世代とIDで実行可否を確認し、旧世代や切替途中のトリガーからは送信しません。

同じスクリプトの更新処理は同時実行できません。重なると後から開始した処理が「別の処理を実行中です」で停止するため、送信準備・送信のトリガーは実行時間が重ならないように設定してください。競合で止まった処理は先の処理終了後に再実行します。シートの直接編集や別のスクリプトからの更新は、このロックの対象外です。

## エラー時の挙動

「データ整理」の「運用の状態と、次にすること」で、送信確認待ち・送信エラー・本文生成失敗・元フォームへの書き戻し失敗などを確認できます。原因の確認方法と対象シートへのリンクを表示し、自動再送や状態の自動リセットは行いません。過去のエラーログ件数は、未解決件数とは区別して表示します。

自動実行の記録には所要時間（`elapsedMs`）を含みます。例外で停止した場合は「失敗」、処理が戻っても送信エラー・要確認・新しいエラー記録がある場合などは「要確認」（`attention`）と表示します。「完了」だけで全行の送信成功を判断せず、対象行とエラーを照合してください。

- 明確なレート制限（HTTP 429、`RESOURCE_EXHAUSTED`等）で投稿が拒否された場合だけ、最大3回試行します。解消しなければ`未`となり、再実行の対象です
- 権限・入力不正など明確な投稿拒否は`エラー`、フォーム側は`送信エラー`になります。エラー内容を判別できない場合は安全側に倒して`送信確認待ち`とします
- 通信途絶・内部エラーなど投稿結果が分からない場合は、`SEND_RESULT_UNKNOWN`を記録し、`送信確認待ち`で止めます
- 投稿成功後の状態保存失敗は`SEND_RECORD_ERROR`として投稿IDとともに記録し、自動再送しません。書込みの成否によって行は`送信確認待ち`または`済`のままになります
- 同じ元回答の送信行が複数ある場合、未送信の行は`DUPLICATE_SOURCE`として確認待ちにします。行の前後や本文の違いだけで送る行を決めません
- フォーム回答シートの `送信状態` 更新に失敗した場合も `エラー` シートへ `FORM_UPDATE_ERROR` を記録します

### 送信準備に失敗した行の復旧

元回答が`準備×`になった場合は、エラーログを確認してメール・生徒一覧・対応表・本文設定などの原因を修正します。対応する送信行がまだないことを確認して元回答の状態を空欄に戻し、送信データを準備してください。旧評価データからの移行で失敗した場合は、旧行の`処理状態`も空欄に戻します。すでに送信行がある場合は、その本文と送信状態を確認して復旧し、元回答の状態変更だけで本文が再作成されるとは扱わないでください。

### `送信確認待ち`の確認と復旧

1. 実行が終了していることを確認し、`エラー`シートとClassroomの投稿内容・対象生徒を照合します。投稿IDが記録されている場合は、その投稿も確認します。処理の強制終了などではエラーログが残らない場合もあります。
2. 投稿済みなら送信行を`済`にし、必要に応じて元回答の状態も`済`に直します。
3. 未投稿と確認できた場合だけ、原因を直して送信行を`未`に戻し、再実行します。結果が分からないまま`未`や空欄に戻さないでください。
4. 重複行は内容を確認し、残す行を1行に整理します。すでに投稿済みなら残す行も`済`とし、再送しません。

送信準備は、既存の送信行と旧評価データの`元SS_ID + 元シート名 + 元行番号`を照合して重複追加を避けます。途中で状態更新が失敗しても、再実行で同じ行を追加しません。ただし、元フォームの古い状態表示は自動修復しない場合があるため、`FORM_UPDATE_ERROR`があるときは出力行と照合して状態を補正してください。

## 注意点

- 生徒のひも付けは `メールアドレス` 基準です
- `生徒一覧` に存在しないメールアドレスは送信対象にできません
- `コースID` が空の生徒は送信できません
- 未採点判定は `メール列名` を回答到着のマーカーとして使います
- 設定保存では `送信シート` と旧`評価データ`の既存行を保持します。送信データ、または未移行の旧データと列構成が合わない設定は拒否します。旧データは移行を完了し、送信データは先にバックアップ・整理してから列構成を変更してください
- 旧`評価データ`の移行用列名 / `送信シート`列名を空欄にした場合は、フォーム側ヘッダ名がそのまま使われます
- フォーム側ヘッダ名を変えた場合は、先にWeb管理画面の内容も更新してください
- Classroom 投稿は `INDIVIDUAL_STUDENTS` モードで行われます
- 重複照合は元回答の行番号と既存の送信行・旧評価データを使います。元回答の物理的な並べ替え・行削除・シート名変更、キューのクリアをまたぐ重複防止は保証しません。元回答情報・送信状態を手動で変更する場合も既存投稿を確認してください

## 設定JSONの再利用

上部の「設定を保存・出力」では、左の「出力」で種類を選んでJSONを書き出し、右の「入力」でJSONファイルを選びます。狭い画面では縦に並びます。入力時はファイルの内容から次の4種類を自動判定し、判定結果と変更内容を確認してから適用します。既存の個別JSONと一括JSONをそのまま利用でき、ファイル名を変えても判定できます。不明な形式や識別情報が矛盾するファイルは読み込めません。

書き出しは保存済みの内容が対象です。管理・採点・テンプレ編集の各画面で、先に未保存の変更を保存してください。自動実行の希望時刻は自動実行画面で確定します。

| 種類 | 内容 | 読み込み時の動作 |
| --- | --- | --- |
| 全部まとめて（引っ越し用） | 管理設定・採点設定・採点テンプレパックを1ファイルに収録 | 3種類とも置き換え。既存テンプレートもすべて置き換える |
| 管理設定 | 列の用途、取り込み項目、評価変換表、返信本文、対象シート名の接頭辞、自動実行の希望時刻 | 管理設定を置き換え |
| 採点設定 | 氏名・回答の表示列、得点・講評の列、テンプレートの選択など | 採点設定を置き換え。回答タブは移行先で選択 |
| 採点テンプレパック | 条件、講評文、出力ごとの表示、各枠の入力制限などのテンプレート本体 | 既存テンプレートに追加。同名がある場合は全件取り込みを拒否 |

管理設定・全部まとめての出力では、最後に作成・利用したひな形フォームの編集URLと通知先メールアドレスを個別に選択できます。ひな形URLを選ぶには、ひな形を作成するか、ひな形からフォームを準備しておく必要があります。読み込むと選択した項目だけを置き換え、選択しなかった項目と回答先スプレッドシートの接続URLは保持します。以前のJSONに含まれる回答先スプレッドシートのURLは従来どおり読み込めます。通知先を含めたJSONで空の通知先を読み込んだ場合は、メール通知を利用しない確認を運用ごとに保存してください。この確認はJSONに含めません。採点画面にも採点設定・テンプレパックの個別入出力を残しています。

ファイル名は `turret-種類-運用名-YYYYMMDD-HHMMSS.json` です。種類は `settings`・`scoring`・`templates`・`bundle`、運用名は運用スプレッドシート名、日時は日本時間です。運用名のファイル名に使えない記号は `_` に置き換え、80文字までに収めます。例：`turret-bundle-化学1学期-20261001-153000.json`。自動ダウンロードが止められた場合も、結果欄のリンクから保存できます。

生徒名簿、回答・採点結果・送信データ、認証情報、トリガーID、稼働状態、フォーム受付終了予約は含みません。これらのデータの移行はスプレッドシート側で行います。読み込み時は内容と追加・置き換えの対象を確認してから適用します。確認後にファイルや関連設定が変わった場合は適用を拒否します。管理設定・全部まとめての適用前には、既存の自動実行を停止してください。適用だけでは開始しません。各手順・採点の列設定を確認し、採点画面を開き直して、最後に自動実行を開始してください。テンプレ編集画面はシートから再読込します。

一括適用は、全内容と既存送信データの列構成を事前確認してから、共通ロック内で保存します。保存に失敗した場合は管理設定・採点設定・テンプレート・希望時刻を元に戻します。復元にも失敗した場合は復旧が必要と表示し、自動処理で設定を使わないよう停止します。適用前の設定はJSONで退避しておくと復旧に利用できます。

新規利用では運用固有のヘッダー・取り込み項目・本文は空です。従来の採点用途を使いたい場合は[採点用サンプルJSON](examples/profiles/assessment.json)を読み込み、自分のフォームに合わせて編集してください。既存の保存済み設定は引き継ぎます。

管理設定の書き出し形式は`application: "turret"`、`schemaVersion: 3`です。共通変換表は`config.gradeScale`、項目別変換表は`config.fields[].gradeScale`に`[{"from":"5","to":"A"}]`のように保持します。項目別設定を省略すると共通表を使い、空配列を指定すると未設定のまま保持します。読み込みはv1・v2・v3に対応します。変換表を持たないv1は、`score_grade`の項目があれば従来の5段階、なければ空の変換表に移行します。v2で明示した空配列は空のまま保持します。

採点設定・テンプレパックも既存の個別JSON形式を維持します。一括形式は `application: "turret"`、`type: "configuration-bundle"`、`schemaVersion: 1` で、`management`・`scoring`・`templates` に各個別JSONを収録します。採点設定で選択したテンプレートがパッケージに存在しない場合は拒否します。

未対応の項目・形式は拒否します。管理設定のJSONファイルは128KiBまで、採点設定・テンプレパック・一括JSONは1MiBまでです。内部保存する管理設定・採点設定はそれぞれUTF-8で8,000バイトまでです。長すぎる本文などは保存前にエラーを表示します。

### 設定保存の復旧

保存途中でエラーになった場合は、変更前の設定値への復元を試みます。復元にも失敗した場合は処理を停止し、管理画面に復旧が必要と表示します。この状態でも自動実行の停止とシート確認はできます。

自動実行の停止が確認できた後に画面の再取得が失敗した場合は、「自動実行を停止しました」と「停止後の画面更新に失敗しました」を分けて表示します。「状態を更新」で再取得してください。旧トリガーの削除に失敗して残っている場合は、その注意も表示します。停止要求そのものが失敗した場合は、停止成功とは表示しません。

その場合は自動実行を停止し、Apps Scriptのプロジェクト設定にあるスクリプトプロパティを確認してください。`APP_CONFIG`と`APP_CONFIG_BACKUP`はどちらも設定本体のJSONです。外部へ出力したプロファイルJSONを使う場合は、その`config`部分を使います（希望時刻は別の保存先）。元の値を退避し、両方を同じ確認済み設定に復元した後で`APP_CONFIG_SAVE_ERROR`・`APP_CONFIG_PARSE_ERROR`を削除し、管理画面を再読込して設定診断を実行します。

主保存値だけが破損した場合は内部バックアップを表示して警告します。内容を確認して管理画面で保存すると両方を復元します。両方が読めない場合は空の設定へ自動置換せず、復旧を要求します。旧版の移行中なら旧シートを保持します。`設定(編集不可)`は表示用のため復旧元に使用しません。

## 主要関数

- `classroomdata()`: Classroom のクラス一覧を取得
- `studentdataMulti()`: 同期対象クラスの生徒一覧を取得
- `prepareSendData()`: 採点済みの回答から宛先・評価変換・返信本文をまとめて準備し、`送信シート`へ保存。旧評価データの未処理分も移行
- `importFromFormsToEval()` / `evalToSendSheet()`: 旧版の呼び出し・トリガーとの互換用。どちらも`prepareSendData()`と同じ送信準備を実行
- `sendMessages()`: `送信シート` を元に Classroom へ送信
- `remindUngradedAndErrors()`: 未採点・未送信・エラー件数をメール通知

## 初期セットアップ例

Apps Scriptへの配置ファイルは、引き続き`Code.gs`・`Administration.gs`・`Setting.html`・`Scoring.html`・`appsscript.json`の5つです。テスト、文書、設定例JSONを配置する必要はありません。

このPCで確認用シートを操作しながら改修する場合は、[開発・画面確認手順](docs/development.md)を参照してください。`clasp`でローカルのコードを確認用Apps Scriptへ同期できます。

1. 管理用スプレッドシートを作成する
2. [Code.gs](Code.gs)、[Administration.gs](Administration.gs)、[Setting.html](Setting.html)、[Scoring.html](Scoring.html)、[appsscript.json](appsscript.json) を Apps Script に反映する（HTML名は `Setting` と `Scoring`。旧 `Automation.gs` は移動済みのため削除し、旧 `SettingsDialog` も重複して残さない）
3. `自動送信システム → 管理画面を開く` を開き、シートを準備する
4. クラス一覧を取得し、シートの `同期対象(1)` に `1` を入れてから生徒一覧を取得する
5. 回答先はフォーム準備時に自動登録。通知先を登録するか通知を利用しないことを確認して保存し、必要に応じて対応表を作成・編集する
6. ヘッダー候補を取得し、列の用途・取り込み項目・返信本文を登録する。再利用するJSONがあれば管理画面から読み込める
7. 採点済み判定には、採点時に必ず入力され、生徒へ送る列を指定する。未採点判定はメール列を使うため、フォームでメールアドレスを必ず取得する
8. 架空データの本文プレビューと、保存済み設定による実データ診断を確認し、自動実行画面で希望の時間帯を指定して開始する

## 処理量の確認と今後の計画

500件・参照元1件のmock試験では、現在の「回答から送信準備 → 送信」の2段階で、キャッシュを使わない比較経路に対し、`openById`とヘッダー単独読み取りはそれぞれ1,002回から2回に減りました。投稿500回、投稿前の状態記録500回、`flush`1,003回は保持しています。`pnpm bench:scoring`では500件・5,000件の採点読込・送信準備と100行の採点保存を確認できます。これらは代替サービスによる検証であり、実GASの処理時間や速度向上率を測定した結果ではありません。

実GASでの500件測定、必要な場合の分割・再開、安定した回答IDへの移行など、未確認事項と優先順は[改善内容と次の実装計画](docs/reports/2026-09-29-improvements-and-next-plan.md)にまとめています。
